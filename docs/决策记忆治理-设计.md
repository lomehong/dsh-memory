| 项目 | 当前状态 |

## 2. 背景与问题

参考项目把 Agent 记忆从"对话日志"升级为"可归因、可授权、可验证、可复原"的治理结构：六类陈述类型（事实/推断/偏好/候选/授权/已验证结果）、六个独立维度（陈述类型、判断状态、生命周期、授权、验证、结果）、单一 owner、替代链双向链接、失败关闭。

对照实测代码，我们当前的记忆体系缺认识论层：

| # | 问题 | 现状证据 | 风险 |
| --- | --- | --- | --- |
| 1 | 静默丢数据 | `memory-store.ts`：`MAX_ENTRIES=500`，超出 `entries.slice(-MAX_ENTRIES)` 淘汰最旧 | 记忆按时间无声蒸发，违反"可复原、不删历史" |
| 2 | 原地覆盖 | `updateMemoryEntry` 直接改写 `content` 等字段，无历史 | 无法回答"这条记忆为什么/被谁改过" |
| 3 | 认识论真空 | `MemoryEntry.type` 混装事件与认识（`decision` 是 type，但无授权/验证/结果维度） | 分不清"建议的"还是"拍板的"、"说好的"还是"验证过的" |
| 4 | 无来源归因 | 知识种子/会话记忆/御驿消息/API 写入同权混存 | 访客转述与主人亲述在存储层无差别，"听说当事实"跨会话传染 |
| 5 | 授权只有频控 | `escalate_to_owner` 有 10 分钟 3 次频控（防滥用），无授权记录（治权） | 不可逆动作没有可查的授权依据 |
| 6 | 记忆整理掩盖冲突 | 保存时按内容近似去重合并（保留最新） | 实质分歧被悄悄抹掉，违反"冲突不强行合并" |

## 4. 核心设计（P0 · dsh-memory）

### 4.1 认识论 schema v2

`MemoryEntry` 全部现有字段保留，新增**可选**字段（旧条目无这些字段，读取时按默认值处理，向后兼容）：

```typescript
export type StatementType = '事实' | '推断' | '偏好' | '候选' | '授权' | '已验证结果'
export type LifecycleState = '当前' | '已替代' | '已归档'

export interface MemorySource {
  origin: 'seed' | 'conversation' | 'yuyi_message' | 'tool_result' | 'human' | 'api'
  ref?: string          // 归因引用：消息ID / 日程ID / 种子文件 / 对端 agentId
  hubEndorsed?: boolean // 御驿 Hub 背书的发送方（仅 yuyi_message）
}

export interface MemoryAuth {
  status: '未授权' | '已授权' | '已拒绝'
  by?: string           // 授权人 userid
  via?: string          // 授权来源（消息ID / 会话引用）
  range?: string        // 授权范围
}

export interface MemoryVerify {
  status: '未验证' | '已验证'
  method?: string
  at?: string           // ISO 时间
}

export interface MemoryLifecycle {
  state: LifecycleState
  supersedes?: string   // 本条替代的旧条目 id
  supersededBy?: string // 替代本条的新条目 id
  reason?: string
}
```

新增可选字段：`statementType?: StatementType`、`source?: MemorySource`、`auth?: MemoryAuth`、`verify?: MemoryVerify`、`lifecycle?: MemoryLifecycle`、`reviewBy?: string`（复核提示日期）。

**读取侧兼容规则**：`statementType` 缺省按 `'候选'` 解释；`lifecycle` 缺省按 `'当前'` 解释；`verify` 缺省按 `'未验证'` 解释。旧文件无需迁移。

**写入侧默认值规则**（治理在 schema 里，不靠模型自觉）：

| 写入来源 | statementType 默认 | source 默认 |
| --- | --- | --- |
| 主人经工具写入 | `事实`（作者即归因） | `{ origin: 'human' }` |
| 访客经工具写入 | `候选` | `{ origin: 'conversation' }` |
| HTTP API 写入 | `事实`（管理页=主人代笔） | `{ origin: 'api' }` |
| 显式传入 | 以传入为准 | 以传入为准 |

**约束校验**（写入时归一，不拒绝）：

- `statementType === '已验证结果'` 但未附验证 → 强制 `verify = { status: '已验证' }` 不成立时回落为 `'候选'` 并在返回中提示；
- `type === 'decision'` 且 `statementType === '授权'` 时必须携带 `auth`（缺省补 `{ status: '未授权' }` 由调用方后续更新）。

### 4.2 memory_update 替代语义

`memory_update` 拆成两类操作：

- **权限类变更**（仅 `scope` / `participants` / `expireAt`）：原地修改，不产生新记录——权限不是认识论陈述，不需要历史链。
- **陈述类变更**（`content` 或 `statementType`）：**替代**而非覆盖：
  1. 以旧条目为基线创建新条目（新 id），应用变更；新条目 `lifecycle = { state: '当前', supersedes: 旧id }`，`author`/`authorRole` 记录修订人；
  2. 旧条目 `lifecycle = { state: '已替代', supersededBy: 新id }`，保留可读；
  3. 返回新条目 id。

旧记录的 scope/participants 随新记录继承；`expireAt` 不继承（由修订人重新决定）。

### 4.3 存储与归档

- 活跃文件 `shared-memory.json`（现有路径不变）保持 `MAX_ENTRIES = 500` 软上限。
- 新增归档文件 `shared-memory-archive.json`（同目录），上限 `MAX_ARCHIVE_ENTRIES = 5000`，超出按最旧 FIFO 裁剪；同锁（复用现有文件锁）保护。
- **淘汰优先级**（活跃集超限时，被移出者进归档而非删除）：
  1. `lifecycle.state === '已替代'` 的最旧条目；
  2. `statementType` 为 `候选` / `推断` / `偏好` 的最旧条目；
  3. 其余最旧条目；
  4. `statementType === '授权'` 的条目受保护，仅在以上候选不足时最后淘汰。
- 手动归档：新增 `archiveMemoryEntry(id)`，把活跃条目标 `已归档` 并移入归档文件；删除工具保留（仅主人、显式），语义不变。
- `pruneExpiredMemories` 行为不变（过期即清理，TTL 本身就是"自declared 短命"语义）。

### 4.4 读取与注入

- `memory_read` 新增可选参数：`statementType`（精确匹配）、`includeSuperseded`（默认 false）、`includeArchived`（默认 false）。默认只返回 `当前` 条目——旧条目（无 lifecycle 字段）视为当前。
- 条目输出增加 `statementType`、`lifecycle.state`、`source.origin`、`auth.status`（存在时）。
- 系统提示词元信息注入升级为按陈述类型分布（仍只报真实计数，不声称相关）：
  `【共享记忆】你共有 N 条共享记忆（当前 M 条：事实×a、候选×b…；最近一条写入于 …）`
- HTTP API 新增 `GET /dsh-memory/archive`（归档列表）与 `POST /dsh-memory/entries/archive`（手动归档）。

## 5. P1 设计

### 5.1 御驿来源接入（dsh-yuyi）

`yuyi_inbox` 工具描述与 prompt 指引增加一段：把御驿消息内容写入共享记忆时，必须传 `statementType: '候选'` 与 `source: { origin: 'yuyi_message', ref: <消息标识>, hubEndorsed: <是否 Hub 背书> }`。晋升为`事实`需主人确认（`memory_update` 仅主人的现有设计承接）。纯指引层改动，不引入插件间服务依赖。

### 5.2 授权记录（dsh-twin）

`escalate_to_owner` 工具描述增加：主人批准/拒绝后，用 `memory_write` 记录授权——`type: 'decision'`、`statementType: '授权'`、`auth: { status, by, via, range }`。频控保留（管滥用），授权记录管治理。`twin-guard` 段同步增加一条表达纪律：不可逆动作（对外发送、发布、删除类）执行前先经 `memory_read` 查是否存在覆盖该范围的`授权`记录。

### 5.3 输出门禁（dsh-twin twin-guard）

取参考项目输出六问中对会话分身真正有用的三问，作为静态指令注入 `twin-guard` 段：

1. 受众与可见范围匹配（主人内容不外流，scope 已有模型）；
2. 每项重要结论标明陈述类型，候选不写成事实，建议不写成已授权；
3. 反证、失败、跳过与证据缺口如实披露；检查通过不等于验收或 Go。

## 6. P2 设计

### 6.1 记忆整理处置对照

把 dsh-twin 保存时的近似去重合并升级为处置对照（移植参考项目共识维护）：

| 条件 | 处置 |
| --- | --- |
| 归一化后陈述与范围完全相同 | 替代链去重（保留最新，旧条目标 `已替代`，不再物理删除） |
| 内容近似但存在实质差异 | 两条都保留，互相标记冲突关联（`lifecycle.reason` 记 `conflict`） |
| 新证据可能改变支持度 | 保留原条目，写 `reviewBy` 提示复核 |
| 均不满足 | 保持不变 |

### 6.2 twin-config 归一化与种子归因

- 导入/导出人格配置时应用归一化纪律：Unicode NFC、CR/LF 归一、控制字符清除（保留换行）、连续换行折叠、行首「#」中和（防在系统提示词伪造章节结构）、单行字段空白折叠——幂等，覆盖向导保存/导入/历史恢复的唯一写入口 `saveConfig`。
  实施说明：不做全量 Markdown 行内转义——人格字段本意承载自然语言排版，全量转义会劣化表达；结构性注入由「行首标题中和 + twin-guard 段 + 访客 fail-closed 视图」三层兜底。
- 知识种子写入时带 `statementType: '事实'` 与 `source = { origin: 'seed', ref: 'wizard' }`。

### 6.3 管理页治理视图

`memory-admin-page` 增加按陈述类型的分布统计、替代链与冲突的展示、`reviewBy` 到期提示、归档区入口（依赖 4.4 的归档 API）。

## 7. 明确不做的事

- 不搬参考项目的文件树 owner 模型（facts/decisions 目录树）：我们是结构化存储 + 工具读写，语义移植、形态不移植。
- 不做字节预算/P0 装配/三件套发布：当前记忆量级小且有工具化检索；记忆破千后再评估检索预算化。
- 不做重仪式任务契约：治理重量匹配行动可逆性（对话零仪式 / 对外承诺走授权 / 不可逆走全记录）。
- 不改 `memory_delete`（仅主人、显式删除）与 `pruneExpiredMemories`（TTL 自declared 短命）的现有语义。

## 9. 风险与开放问题

- 工具参数增多可能降低模型调用率：以默认值规则兜底，模型只需在"来自御驿/涉及授权"时显式传参。
- 归档文件增长：5000 上限 + FIFO，管理页提供容量展示（P2）。
- `dsh-yuyi` 与 `dsh-memory` 无服务依赖，来源接入靠指引约束：若后续出现高频误标，再评估可选注入校验。
